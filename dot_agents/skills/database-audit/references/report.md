# Database audit report contract

Lead with actionable findings and recommended first bounded batch. Scale detail
to repository; no forced finding count or universal score.

## Scope and coverage

Name snapshot/commit and reviewed overlay, owned stacks and actual versions,
drivers/environments, consumers, selected guidance/revision and project authority.
Identify unsupported engines and excluded artifacts.

| Component/environment | Engine/platform or boundary lens | Review disposition | Evidence/limits |
|---|---|---|---|
| Concrete owned paths | Applicable selected lens | reviewed / sampled / unavailable / not applicable | Inspected paths, samples, exclusions and unreviewed units |

Use independent denominators for inventory, inspected source and completed checks.
Zero units is not 100%. Separate static source from live schema, query-plan,
workload, permissions and operational evidence. Loading guidance proves neither
review nor checks. List actual commands, targets/environments/versions, scope,
status, results and limits. Proposed/not-run checks, unavailable tools, failures
and suppressions remain visible. Complete static scope does not establish live
qualification. Reuse QA capability semantics when structured evidence is needed.

## Findings and retain decisions

Use stable local IDs and one primary category: confirmed source/contract defect,
advisory design recommendation, modernization option, or performance hypothesis.
Measured performance requires representative workload/environment evidence.

Name concrete locations/consumers, owning layer, evidence versus inference,
trigger/consequence, impact/confidence with reasons, proposed change and useful
retain alternative, compatibility/recovery constraints and focused validation.
Cite specific engine rules used, checking actual version/workload assumptions.
Explain conflicts; multiple lenses do not independently prove one root cause.

Never invent sizes/cardinalities, index benefits, savings or runtime behavior.
Static suspects include missing measurement plans. Transaction/retry proposals
name actual guarantees and duplicate/partial effects. Migration advice includes
consumer/backfill order and recovery. Keep secrets/raw production data private.

## Ordered refactor batches

Each batch names goal/finding IDs, components and responsible layer, prerequisites,
effort/risk with assumptions, preserved contracts, compatibility and validation.
Put characterization, engine verification or measurement before dependent work.
Prefer independently reviewable improvements over broad stack replacement.

Close with retain choices, unresolved questions, evidence gaps and disposition:
complete for declared scope, partial, or not applicable. A Python audit subreport
returns these fields to its primary without recursion or duplicate remediation.
Implementation remains separate authorized DBSCTR work.
