# Native MCP configuration and authentication

Skill files do not install the official plugin or its remote MCP. Resolve the
actual client's executable/version, process-selected home and effective native
configuration layers. Inspect only the relevant entry and preserve all unrelated
settings. A URL or config file alone does not prove native discovery, OAuth,
connectivity or actual upstream tools.

The retained upstream helpers assume plugin-owned JSON files and can substitute
placeholders, rewrite files or create/merge Kiro/Junie global entries even from a
`detect`/`resolve` call. Do not run them as harmless installation checks. No
automatic CLI-derived URL retargeting, plugin reinstallation or global config
writes are part of this portable skill.

For OpenCode V2, use the actual native `mcp.servers` owner and its `disabled`
state. The old helper's `mcp.jfrog` / `enabled:true` shape and inferred
`mcp-auth.json` storage do not qualify V2. Do not edit credential stores directly.
See [OpenCode native ownership](../../jfrog-mcp-management/references/harness-opencode.md).

For Codex, keep separately bound CLI/Desktop homes and their native writer and
managed projector when applicable. Do not assume all surfaces share config or
that environment labels authenticate a native origin. See
[Codex ownership](../../jfrog-mcp-management/references/harness-codex.md).

A specifically authorized connection uses the native owner, selected endpoint,
reviewed entry, private preimages and proper native authentication. Preserve
existing trust/approval policy; neither this skill nor helper metadata can grant
permissions. Report absent tools or failed authentication honestly, without
starting OAuth, another backend or a different server merely to obtain green.
