# Specialist Selection and Progressive Disclosure

Consult this reference for unresolved selection, discovery or handoff questions.
Reuse relevant loaded guidance while source, task evidence and project policy apply.
This is a loading contract, not another coordinator or a runtime dispatcher.

## Select from task evidence

The native catalog exposes available names/descriptions. DBSCTR's matching module
adds concise evidence triggers. Select the smallest useful set for the actual
operation: authoring, diagnosis, migration, measurement or deployment. A platform
mention, installed executable or incidental file is insufficient on its own.

Use project facts and changed interfaces before asking questions. Resolve material
missing target/policy choices; preserve authorization already given. Multiple
layers can apply when the task crosses them, without loading every skill for the
stack. A GKE image-pull failure does not need async Python guidance merely because
the application is Python; changed concurrent Python behavior does.

Load a selected entrypoint through the native loader, or read its installed
`SKILL.md` from the available catalog when no loader is exposed. Resolve resources
relative to that bundle. Read only sections/resources needed for the current
decision. Do not enumerate/read every installed skill body to choose one, fetch
moving upstream instructions during execution or execute a helper before review.

Explicit skill disablement and scope exclusions take priority. For permitted
managed guidance missing from discovery, use the [read-only sibling resolver](../scripts/resolve_specialist.py)
through an existing Python interpreter, passing only the known skill name. Its
path is relative to the loaded DBSCTR bundle; do not install a runtime to run it.

The resolver follows the physical DBSCTR directory before inspecting the exact
sibling and verifies the entrypoint name. Registration directories can be symlinks:
a failed lexical parent lookup does not establish absence. Read the returned
entrypoint and needed resources. If resolution cannot be verified, report that
limitation rather than claiming the bundle is globally uninstalled. Do not scan
unrelated runtime homes, fetch a replacement or treat lookup as authorization.
Discovery, available files and permitted use remain distinct observations.

## Preserve authority

Keep one primary. A specialist supplies methods and evidence; project policy
selects runtimes, tools, targets, dependencies and acceptance. QA runs selected
authorities. DBSCTR owns lifecycle/gates. Loading does not grant installation,
deployment, host/cluster mutation, authentication or publication authority.

Use an existing specialist or equivalent guidance if sufficient. An unavailable
preferred skill is a guidance limitation; missing required validation is still a
capability gap. Preserve actual failures, child exit status and uncertainty.
Rendering, command submission, installation and readiness are distinct claims.

Return only decision-relevant scope/target, selected guidance/revision, findings,
actual evidence, affected artifacts and unresolved limitations. Feed the existing
cycle/artifacts; do not create a parallel Gate Ledger, issue workflow or helper
by default. New evidence can revise selection and revisit an affected phase.

## Efficiency and reliability limits

Catalog metadata has a cost even when bodies are lazy-loaded. Keep descriptions
short and discriminating, routing tables compact and substantial examples in
on-demand references. Do not reload unchanged guidance merely for a phase label.
Client caching, compaction and catalog scoping remain native-client behavior.

Selection is model-driven. Instruction wording or a deterministic inventory test
does not guarantee every future trigger. Use independent positive, negative and
mixed-layer task cases to detect missed/irrelevant selection, policy drift,
unnecessary resource loading and dishonest evidence. Report sample and execution
limits; static character counts are not measured tokens or effectiveness gains.

Reviewed pins, complete bundle resources/licenses and reversible adaptations live
in source-owned provenance inventories. Maintenance reviews source changes;
ordinary skill use consumes the installed reviewed revision.
