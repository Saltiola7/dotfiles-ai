# Forgejo local-only registration Initiative

This Initiative delivers one bounded slice in `dbsctr_v3_lifecycle`: native
Forgejo local-only cycle registration and completion, with reviewed manual
delivery remaining a separate explicit Git operation. The operator approved this
local-first amendment. The complete Forgejo remote-automation outcome remains
blocked and its earlier qualification evidence is preserved.

The home and coordinator repository is the existing public dotfiles-ai GitHub
repository. The bootstrap [MANIFEST.json](MANIFEST.json) intentionally uses schema
1 so the installed helper can register the public support cycle through its
unchanged GitHub path. The new consumer-facing schema 2 and schema 6 interfaces
are specifications to implement, not installed capabilities.

| Context and owner | Bounded outcome | Dependency |

| `dbsctr_v3_lifecycle`, lifecycle maintainer | Typed private authority, controlled read-only HTTPS base fetch, exact native local-only launch, zero-network local completion and preserved unpublished source | Existing GitHub support delivery, then approved managed installation |
| Private consumer owner, adjacent authority | Own private profile, credentials, validation, exact launch approval and any later manual Git delivery | Verified installed local-only capability; consumer content stays outside this Initiative |

This is an incremental extension of the existing context, not a replacement

The `local-registration` slice is specification-ready and Build-owned. Exact

No PM ticket is required or created by Discovery.

## Support-cycle handoff

Use critical risk, Python and Security modules, and the existing public GitHub
`draft_pr` delivery path. Select the intended public support account explicitly;
do not switch or trust the global default account. Worktrunk owns the clean linked
Build checkout at a freshly fetched approved base. The committed profile and a
private `.dbsctr/plans/` applicability plan bind every gate. The source cycle
requires the Development Kernel, Review/Integrate and Maintain/Retire. Release,
Deploy and Operate are not applicable with explicit source-only reasons: no
independent package, installation or activation is delivered by this cycle.
Subsequent rollout separately requires Deploy and Operate for approved managed
installation of the merged helper, verified loaded bytes and bounded first-consumer
qualification. These proofs remain mandatory before private consumer use; they
do not circularly block publication of the candidate that must first be reviewed
and integrated.

After exact public-content checks include all intended new documents, run the
existing `initiative-check`, issue a fresh `initiative-receipt`, and run actual
`begin --preflight` in the selected native Build checkout. Present its exact
scope, risk, target and launch digest for approval before registration. Import
only the complete approved public documentation closure; do not copy private
consumer bindings, raw evidence or credentials. A helper does not stage, commit,
launch a cycle, publish or install on the primary's behalf.

Build updates the existing helper, schemas, affected tests and lifecycle guidance
incrementally. Review the existing bounded-context README and CHANGELOG, update
their durable truth/completion entry where required, and retain all failed or
unavailable evidence honestly. No code, stages, commits, cycles or preflight are
claimed by this Discovery document.

## Validation and publication

The exact candidate must pass the project's existing publication/instruction
authority, including new files in its index inventory, and independent scope/privacy
review. Manifest structure is separate from publication safety. The feature
lists configured pytest, compilation, rendering and CI authorities and meaningful
acceptance cases. Source PR review/integration precedes managed installation;
consumer source and its later local cycle retain their own private authority.
