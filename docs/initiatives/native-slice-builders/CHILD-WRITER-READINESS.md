# Native child builders: launch readiness

**Highest priority: independent implementation with separate context windows.**
This extends the existing native-slice Initiative; it does not replace the
planning draft or the controller already merged in #362.

## Use case first: one repository, two worktrees

The operator normally develops in multiple Worktrunk worktrees of **one
repository**. The representative case is two independent slices on two
feature branches aimed at the same `main`: each worker needs a focused
conversation and its own checkout while the slices build and test in
parallel. There is no requirement to split the code into separate
repositories. Simultaneous merges are unnecessary.

| Worker | Context and feedback | Worktree routing |
|---|---|---|
| OpenCode native subagent | Separate conversation linked to its caller; the result returns to the parent. | Create starts the child at the parent's location. Moving it to a sibling worktree while preserving linkage, tool routing and feedback is untested. |
| Top-level OpenCode session in a Herdr tab | Fresh conversation per slice. The coordinator can wait and retrieve the worker's exact answer by session ID. | Verified for two Build workers in linked worktrees of the same repository. |

The [earlier Discovery-Coordinator design](../../specs/opencode_control_plane/features/initiative-launch-atomicity.md)
already describes opening a Build tab in Herdr. The
[managed coordinator profile](../../../private_dot_config/opencode/agents/discovery-coordinator.md)
now hands off a preflight and explicitly retires that custom launcher. Keep
the operator experience as a candidate; selecting a launch mechanism or
reviving the old implementation is a separate decision.

## Marker test: routing, overlap and feedback

Tested on Linux with OpenCode 2.4.1, Herdr 0.9.5 and Worktrunk 0.80.0.
Worktrunk created two feature worktrees from the same disposable `main`
with its normal pre-switch checks. Herdr opened an unfocused tab in each.
The coordinator sent a short task to each fresh session rather than
forking its own conversation. Both workers had distinct native session IDs
and no `parentID`.

| Pass | Native agent recorded on the tool turns | What happened |
|---|---|---|
| First prompt in each tab | `plan` | Each probe wrote its own marker. The two process intervals overlapped by 201,709 ns. This is a Plan observation only. |
| Explicit Build selection, same two sessions | `build` | Both probes exchanged a byte over a fresh pipe and wrote new markers. Their intervals overlapped by 24,542 ns. The first markers stayed intact. |

Select and verify `build` before sending a Build task. The first prompt
in a new tab did not automatically use that role in this setup.

Each shell call used its session's default directory. Independent Git and
filesystem reads matched the branch, checkout and common base, found only
the expected markers in each worktree, and found `main` clean. The bounded
pipe exchange proves that two processes were running at once; it does not
measure a speedup or establish concurrent DBSCTR Build/Test gates.

**How results came back:** concurrent `herdr agent prompt … --wait` calls
reported completion. The coordinator matched each pane's session ID to
OpenCode, then read the final assistant message from
`GET /api/session/{sessionID}/message`. Both Build replies matched their
own branch, checkout and a fresh value generated by the probe. No operator
copy/paste or terminal-text scraping was needed. This is an explicit
wait and read by the coordinator, not an automatic native-child notification.

**Decision:** use one fresh Herdr-launched Build session in its own worktree
to deliver a draft PR. The [standalone worker brief](HERDR-LOCAL-WORKER.md)
names the test, writable scope, gate plan and how to verify the published head.
A native-child comparison can be revisited if automatic feedback is needed.
No cycle was registered in the marker test. Same-target cycle claims,
write confinement, recovery and protected delivery remain unqualified.

## One worker delivered a draft

In a separate run, one fresh Herdr-launched Build session registered the
approved cycle in its Worktrunk checkout, passed nine required local gates
and published [draft #373](https://github.com/Saltiola7/dotfiles-ai/pull/373)
at `1abbe7b1`. The coordinator collected the result by session ID and
matched the completed Cycle Record and GitHub draft head. DBSCTR itself
reported native session attribution unavailable. No merge was performed.

Together the runs prove concurrent tool execution and one full cycle
through draft publication, not concurrent cycles. Two workers were a
minimum feasibility check, not the required capacity or a worker limit.

## Next proof: four independent cycles in one repository

The [four-worker brief](HERDR-FOUR-WORKERS.md) scopes four disjoint slices
against the same `main`.
For each, name its writable paths, dependencies, shared resources and
validation before preflight. Use one fresh Build session, Worktrunk
checkout and separately approved Cycle Record per slice. Shared write
paths, including a common changelog, need a single owner or serialized
updates. Do not bypass an existing claim or tool refusal.

Verify actual four-way overlap separately for Build and Test, then check
each result against its own record and commit. If fewer than four overlap,
report observed concurrency and what limited it; four open tabs do not
count. Keep publication and protected integration serial. Four is a
qualification target, not a production limit or a speedup claim.

## Earlier qualification proposal

The sequence below describes one possible implementation order, not a
requirement to use separate repositories or native parent/child linkage.

| Increment | Runnable proof | What remains fenced |
|---|---|---|
| One child-owned cycle | A dedicated native OpenCode child gets a prepared Worktrunk worktree and a durable launch reference. It registers one disposable cycle, edits owned files, runs gates, and returns a verifiable result after a context restart. | Ordinary helpers keep their current permissions. Start with local fixture delivery; no forge credentials or protected mutation. |
| Independent targets | Two routine fixture slices run Build and Test at the same time in separate child sessions and worktrees. Verify claim recovery and reject sibling writes and reused evidence with changed inputs. | Dependency and shared-resource conflicts serialize. Integration uses the existing coordinator. |
| Same target | Qualify disjoint concurrent implementation claims on a single target, including restart, overlap refusal, and stale-authority refusal. | Keep the protected candidate slot serial. Treat publication and merge as separate authority. |

**Text equivalent:** qualify a child with one isolated worktree and cycle,
then prove concurrent execution across independent fixture targets. Separately
qualify concurrency on one target without parallel protected integration.
The Lifecycle and Auto owners maintain this sequence when identity, custody,
or deployment boundaries change.

## Launch blockers

- `slice-writer-and-evidence` is not ready in the committed manifest. It
  depends on `discovery-delegation-plan`; the planning increment is still a
  draft. To start a narrower local source slice before that draft lands,
  explicitly separate its requirements from planning delivery and from
  multi-slice draft-grant policy. Do not remove the existing dependencies
  simply to make receipt issuance pass.
- The merged native writer currently rejects non-null `parentID`. A child
  route must expose independently verifiable session, parent, checkout,
  and accepted activation identities before Build. Do not relax the
  top-level adapter check or assume a session fork can rebind a checkout.
  Identify the native route and its actual write boundary before declaring
  the child slice ready.
- An earlier request to prepare a checkout with `--no-hooks` was denied;
  the ordinary Worktrunk path succeeded in the disposable fixture. Once
  the chosen slice is ready, use normal checks to prepare a clean linked
  task checkout at the verified base, issue its receipt, and run
  `dbsctrctl begin --preflight`.

The launch authority must name the exact managed source and tests, the
Engineering Profile and applicable gates, compatible inputs, and the
fixture-only boundary. No child is registered, configured, or dispatched
by this note.

## Approved scope: standalone local proof before #359

Preserve the existing planning dependency for the broader writer and
delivery slices. Scope a separate local-only milestone first. The existing
controller owns approval, registration, and recovery; Worktrunk owns the
prepared checkout. Only a dedicated child may build and request the gates
for that approved cycle. Ordinary helper roles, checkout permissions,
and the top-level writer's rejection of child identity stay unchanged.

The minimum first proof is a native, independently observed parent and
child session bound to the exact prepared checkout and first Build request.
The request stays held until the controller verifies registration. Prove
that a wrong parent, substituted root, wrong checkout, or ambiguous
dispatch cannot acquire or reuse the claim. Use a disposable Linux fixture
with no forge credentials or remote mutation. Local completion records the
tested head and tree; it is not provider admission, protected delivery,
or authority to promote a dependent slice.

The merged writer and private journal can be reused, but the ordinary
managed runtime is GitHub delivery-oriented and lacks that local terminal
transition. Current native authority also bars child attachment and
registration through the ordinary helper route. Do not simply allow a
non-null `parentID`, grant shell commands to ordinary subagents, or use
parallel threads around process-wide checkout selection. Source review
does not establish a native child-to-worktree binding or write confinement.
Verify that boundary with a read-only native interface inspection first;
if unprovable, retain the hold and propose a separately qualified route.

Once a local child is proved, authorize two disjoint fixture targets
separately and use the existing target fences. Demonstrate actual overlap
with separate context windows and worktrees before production concurrency.
Same-target implementation and the protected integration slot stay serial
under the existing contract. No preflight digest exists for this milestone.

## Native binding readback

The [published OpenCode V2 API schema](https://opencode.ai/docs/openapi.json)
documents that `POST /api/session` ignores `location` when `parentID` is set:
a linked child starts at its parent's location. Native Create therefore does
not provide an atomic parent-to-child binding across two Worktrunk worktrees.
The API describes session Move separately, but that description does not
establish that moving a child preserves parent linkage, controls request
ordering, or confines writes to the destination. Current DBSCTR native
authority denies child attachment and writer transfer. A session location
readback is not proof of filesystem confinement.

The child Create finding is a schema readback. The marker test above used
top-level sessions on 2.4.1; neither it nor the earlier 2.3.2 service smoke
exercised Move on a linked child.
